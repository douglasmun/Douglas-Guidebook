Six questions, short answers
Am I affected?
Only if something installed agent-framework 1.26.1 or 1.26.2: from PyPI between 20:35 and 21:16 UTC on 17 Nov (04:35–05:16 SGT, 18 Nov), or later from a mirror or cache that kept a copy. Pinned 1.26.0 or earlier is clean.
What did it take?
Secrets from the environment and from credential files, including any Azure DevOps pipeline token, plus freshly minted Azure and GitHub Actions tokens, posted to a public webhook (page 9).
How did it get in?
Through Microsoft’s own release service, most likely with a stolen client certificate. Every gate checked something other than where the package was built (KJ-2, KJ-3).
Who did it?
Unattributed. The tooling named itself Cairn, an open-source AI pentest framework, and an AI agent most likely ran it (KJ-4). An opportunistic operator is likely (KJ-6).
What should we do now?
Hunt for the versions and files, rotate every secret on hosts that ran them, and review Entra ID and OIDC sign-ins (page 14). GitHub Actions controls for every stage are in Appendix C (page 20).
Is it over?
Both versions are gone. Microsoft has not said how the credential leaked or whether it is revoked (KJ-7, Q-1, Q-2).

Two poisoned releases, shipped by Microsoft’s own release service, were live for up to 39 minutes

On 17 November 2026 an unauthorised party published two trojanised versions of Microsoft’s agent-framework Python package, 1.26.1 and 1.26.2, to PyPI through Microsoft’s own release service. Any environment that installed them ran a credential stealer at every Python start. It sent secrets, including any Azure DevOps pipeline token in the environment, and freshly minted Azure and GitHub Actions tokens to a public webhook. Wiz assesses that the attacker held a stolen client certificate for ESRP, Microsoft’s release pipeline. The attacker’s tooling was the open-source Cairn framework, and we assess that an AI agent did the work in about ten minutes. Organisations that installed either version, from PyPI between 20:35 and 21:16 UTC (04:35–05:16 SGT, 18 November) or later from a mirror that cached it, should treat every secret on those hosts as exposed and rotate it within 24 hours.

The third way into Microsoft’s open-source supply chain this year

An analogy: a copied staff pass at the courier depot

A courier firm lets anyone with a valid staff pass load parcels into its vans, provided they come in through the firm’s own gate. A stranger with a copied pass is turned away at the public gate, walks round to the staff entrance, and four minutes later is waved through. The scanner looks for known dangerous items, not for whether the parcel was packed at the depot. The parcel leaves in a branded van, and recipients sign for it because the van is real.

Why it matters in Singapore

The attacker’s working host sat in AWS’s Singapore region: check local logs for 13.215.157[.]103 around 17 November, remembering that AWS reassigns addresses (page 12). The exposure window fell at 04:35–05:16 SGT on Wednesday 18 November, when scheduled overnight builds run unattended, so CI systems are the likeliest local installs. And the UTC+8 clock in the malicious wheel is a default of the attacker’s tool, not evidence of a local operator (page 11).

How Microsoft publishes to PyPI, and why every gate let this release through

ESRP, the Engineering System Release Pipeline, is Microsoft’s central service for signing and publishing packages. Public Microsoft pipelines show how it works: a release task sends the package to api.esrp.microsoft.com with an intent of PackageDistribution, a content type such as PyPI, and named owners and approvers; ESRP checks it and publishes it under Microsoft’s account. The Azure SDK team moved its Python releases from its own PyPI account to the central ESRP team, so those packages now publish under the single Microsoft account. Pipelines authenticate with a client certificate, and one Microsoft project’s release job must run on a specific build pool because that pool holds the certificates needed to publish to PyPI through ESRP.

We assess that the attacker held a copy of such a certificate and its key (KJ-2). From then on, each gate asked a question the attacker could answer: did the submission come from a Microsoft network, did an approver accept it, did a scanner recognise anything bad. None asked whether Microsoft’s own pipeline had built the file from Microsoft’s own source.

Walking the chain, stage by stage

Each stage ends with its lesson and a GitHub Actions control, C-1 to C-7, for teams that publish or install Python packages from GitHub. Microsoft released through ESRP, not GitHub Actions, so C-1 to C-4 are the equivalent controls for your own pipeline, not a picture of Microsoft’s. 1 CredentialOpen

A release credential that worked away from Microsoft’s build pools

Wiz assesses that the attacker held a client certificate and private key for ESRP. Microsoft’s public pipelines show that such certificates normally sit on designated build pools. How a copy left Microsoft is unknown: theft from a build host, a secret exposed in a repository or log, insider misuse, and compromise of the vault that stores it all fit what is public (page 15).

Lesson Make release keys non-exportable, held in hardware or a managed signing service, or replace certificates with a workload identity only one pipeline can use. A copied file should be worthless.

Walking the chain, continued: from install to the attacker’s bin

6 ExecutionConfirmed

A .pth hook runs the stealer at every Python start, pip included

Python reads .pth files in site-packages when the interpreter starts, so the stealer ran whenever any Python process started in the environment, whether or not the code imported agent-framework. It set _AF_TEL=1 to run once per process tree and detached into its own session, so it outlived the CI job that started it and left nothing in the job log. The genuine agent-framework-core 1.26.0 stayed installed, so applications kept working.

Lesson Hunt for .pth files that import code, not only for the package name. Before running pip in a suspect environment, export _AF_TEL=1: plain pip triggers the hook. In CI, check for new hooks before any Python process starts.

7 Theft, exfilConfirmed

The stealer gathered secret-looking environment variables, up to 300 other processes’ environments and up to 80 credential files, then requested new tokens from Azure managed identity, Azure DevOps OIDC and, in 1.26.2, GitHub Actions OIDC. Why a .pth file is worse than a poisoned import

Malicious code in __init__.py runs only when something imports the package. A .pth line runs in every interpreter that loads site-packages: the application, its tests, pip itself and a one-line python -c. Removing the package removes the file, but every Python start before that ran the stealer again, limited only by the run-once variable. MITRE ATT&CK tracks the technique as T1546.018, Python Startup Hooks, and lists earlier PyPI stealers that used it.

What the attacker’s webhook saw: 50 requests in 24 minutes, three real victims

The attacker sent stolen data and its own progress reports to the same free webhook.site URL. Anyone holding a free-tier URL can read what it receives, and Wiz Research did: it logged 50 requests between 20:25 and 20:49 UTC before the endpoint stopped recording. The chart rebuilds Wiz’s published data in our own form, one lane per source.

Reading the 50

Only 17 requests, from three environments, carried victims’ data. The Azure DevOps build pool sent ten, nine of them within seven seconds, which fits a build starting many Python processes at once. More than half the traffic came from security vendors detonating the package.

Everything after 20:49 is out of view. Wiz’s text gives the free tier’s cap as 100 requests, while its chart says the endpoint likely hit a 50-request cap; when JFrog checked the URL, it answered HTTP 429, “Request limit exceeded”. Later victims still ran the stealer and minted tokens, but their data most likely never arrived (KJ-5). Check proxy logs: a 200 response means the bin accepted the data; a 429 means it refused it.

Anyone could read the stolen data, not only the attacker

The bin’s URL sits base64-encoded in the stealer, so anyone who analysed the public package could decode it and read what arrived, until free-tier URLs expire after seven days. Treat secrets that reached the bin as published, not merely stolen, and rotate them even if you see no misuse.

The operator: an AI agent in a near-stock Cairn worker (KJ-4)

Cairn is an open-source, AGPL-licensed framework that coordinates AI coding agents towards a goal. It was built for autonomous penetration testing, placed third in a Tencent Cloud hackathon according to its README, and runs Claude Code, Codex or Pi as its workers. The detection lesson: the warning came six minutes early, and nobody shipped the proof

The refusal was the alarm

The strongest signal of the whole operation was a refusal. At 20:28:56 ESRP rejected a submission that carried a valid credential from an unexpected network. A credential that suddenly appears somewhere new and fails a policy check is far more likely stolen than misconfigured. Wired to an automatic freeze, the refusal would have stopped the release six minutes before it went live. Nothing public shows that it raised an alarm (Q-4).

The proof was never shipped

PyPI supports signed provenance, but Microsoft’s releases carry none, so consumers had nothing to verify. What they could see was cheap and static: a wheel-only release after a history of source distributions, a WHEEL generator that does not match the archive, and a new .pth file. Any one of these justifies holding a release for review before it reaches a build.

How a company Microsoft’s size gets breached: one portable secret behind coarse checks

Large companies rarely fall to a single exotic flaw. They fall through the one path where a portable secret, an automatic approval and a coarse network rule line up, and at Microsoft’s scale there are thousands of pipelines in which that can happen. The pattern is familiar. In 2023 the China-based group Storm-0558 used a stolen Microsoft signing key to reach US government mailboxes; the US Cyber Safety Review Board later found that Microsoft had not detected the compromise of its cryptographic “crown jewels” itself and had relied on a customer to notice. On 17 November the first public warnings again came from outside Microsoft, from vendors such as Wiz and OX Security.

Microsoft’s Secure Future Initiative names the protection of engineering systems as one of its pillars, and its first progress report, in 2024, said more than 85% of production build pipelines for its commercial cloud used centrally governed templates. A central release service such as ESRP removes scattered registry tokens, the kind of secret that opened durabletask in May, but it concentrates the prize: here, one credential whose copy worked outside any governed pipeline. This year attackers reached Microsoft’s open-source supply chain three times, each by a different path (page 2).

We assess that the lesson is not specific to Microsoft. Any organisation that publishes through a central release service holds the same kind of credential. On 17 November the operator, most likely an AI agent (KJ-4), found a network path that accepted it four minutes after the first refusal.

# C-1, C-2, C-4: publish only what CI built, through an
# identity PyPI trusts, after a diff and a human approval.
name: release
on:
  push:
    tags: ["v*"]            # C-2: releases start from a tag

permissions: {}             # jobs get only what they declare

jobs:
  build:                    # C-2: CI builds sdist and wheel
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write       # signs the build provenance
      attestations: write
    steps:
      - uses: actions/checkout@v4
        with: { persist-credentials: false }
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: >-
          python -m pip install --require-hashes
          -r .github/build-requirements.txt
      - run: python -m build
      - uses: actions/attest-build-provenance@v2
        with: { subject-path: "dist/*" }
      - uses: actions/upload-artifact@v4
        with: { name: dist, path: dist/ }

  check:                    # C-4: diff before anyone approves
    needs: build
    runs-on: ubuntu-latest
    permissions: {}
    env: { PKG: your-package }
    steps:
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - uses: actions/download-artifact@v4
        with: { name: dist, path: dist }
      - name: Require an sdist; refuse .pth hooks
        run: |
          ls dist/*.tar.gz
          for w in dist/*.whl; do
            if unzip -Z1 "$w" | grep -E '\.pth$'; then
              echo "::error::$w ships a .pth hook"
              exit 1
            fi
          done

        run: |
          url="https://pypi.org/pypi/$PKG/json"

            || exit 0                 # first release

            --only-binary=:all: -d prev
          top() { unzip -Z1 "$1" | grep -v '\.dist-info/' \
                    | cut -d/ -f1 | sort -u; }
          diff <(top prev/*.whl) <(top dist/*.whl) \
            || echo "::warning::new top-level files since $prev"

# C-3: know within minutes when a release appears that
# your pipeline did not make.
name: pypi-watchdog
on:
  schedule:
    - cron: "*/15 * * * *"
  workflow_dispatch:

permissions:
  contents: read
  issues: write

jobs:
  watch:
    runs-on: ubuntu-latest
    env:
      PKG: your-package
      GH_TOKEN: ${{ github.token }}
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0, persist-credentials: false }
      - name: Latest release needs a tag, sdist, provenance
        run: |
          meta=$(curl -fsS "https://pypi.org/pypi/$PKG/json")
          ver=$(jq -r .info.version <<<"$meta")
          bad=""
          git rev-parse -q --verify "refs/tags/v$ver" >/dev/null \
            || bad+="no tag v$ver. "
          jq -e '.urls[] | select(.packagetype == "sdist")' \
            <<<"$meta" >/dev/null || bad+="no sdist. "
          api="https://pypi.org/integrity/$PKG/$ver"
          for f in $(jq -r '.urls[].filename' <<<"$meta"); do
            curl -fsS -o /dev/null "$api/$f/provenance" \
              || bad+="no provenance for $f. "
          done
          [ -z "$bad" ] && exit 0
          echo "::error::$PKG $ver: $bad"
          n=$(gh issue list --state open --json number \
                --jq length --search "$PKG $ver in:title")
          [ "$n" -gt 0 ] || gh issue create \
            --title "Out-of-band release? $PKG $ver" \
            --body "$bad Freeze publishing; run the runbook."
          exit 1

Before you rely on them

  1. C-1 On PyPI, add a trusted publisher for the project naming the repository, release.yml and the environment pypi; then delete every API token for the project.
  2. C-4 In GitHub, create the pypi environment with required reviewers and a rule that admits only tags matching v*.
  3. C-2, C-6 Generate .github/build-requirements.txt and requirements.lock with hashes, for example with uv pip compile --generate-hashes.
  4. C-6 Create .github/pth-allowlist.txt from the hook list of a known-good run; an empty file is valid.
  5. C-7 Run harden-runner with egress-policy: audit first, copy the endpoints it reports into the allowlist, then switch to block.
  6. C-3 The watchdog checks only the latest release and flags any release without provenance, so it will raise an alarm on every release until C-1 and C-2 are in place. It did exactly that for agent-framework 1.26.0 in our test.
