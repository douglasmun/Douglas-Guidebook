Disclaimer

This report rests on public reporting and on our own read-only examination of SAP’s public GitHub repositories and npm records, both on 27 November 2026. We hold no telemetry, sample or indicator, and we did not read Der Spiegel’s article at source. Quotations from German sources are translations, in part by machine. Drafted with AI assistance and audited by its author, with no independent second review; verify before operational use. Times are UTC, with Singapore time (SGT) in brackets.

Scope, method and sourcing

Scope: the SAP incident first reported on 26 November 2026, the public trace of SAP’s response, and what both mean for organisations that run SAP or build on its open-source packages.

Method: grading three primary sources; reading 13,897 commits in 186 public SAP repositories, the refs of 295, npm records for 24 packages and GitHub’s search index; and testing the commands and controls we publish. Our observations carry IDs E-01 to E-17 (Appendix A, page 13).

The public trail starts eight days before the first report; customer impact is unproven

SAP said on 26 November 2026 that it had identified suspicious activities, acted at once and found no evidence so far of unauthorised access to customer business data. Der Spiegel, citing an insider, reports that attackers stole SAP employees’ authentication tokens and used them to copy and alter SAP source code on GitHub, which SAP has not confirmed. SAP’s public repositories show a response from 18 November, eight days before the first report, when the sync from its internal Gerrit to OpenUI5 stopped. From 20 November signed commits rose from 6% to 34% of direct pushes, matching a rule that Handelsblatt reports. We found no attacker commit, no public copy of non-public code and no report that altered code reached customers, so a constituency advisory is not yet warranted. Teams that build on SAP’s open-source packages should pin dependency versions now, and GitHub organisation owners should review token use within 7 days (page 10).

WhoSAP SE, Walldorf, Germany. Handelsblatt’s sources say numerous development teams are affected. The actor is unidentified.
WhatAn “active IT security incident”, handled inside SAP as “Project Granite” (Der Spiegel, citing a staff notice). Reported: stolen employee tokens, and source code copied and altered.
WhenPublic since the evening of 26 Nov 2026 (CET). SAP’s response very likely began on 18 or 19 Nov (KJ-3). SAP has given no detection date.
WhereSAP’s presence on GitHub, by Der Spiegel’s account. No repository is named. What we observed points to SAP’s internal GitHub Enterprise (KJ-4).
WhyNot known. The reporting we read carries no demand, leak or claim of responsibility.
HowStolen authentication tokens, on one insider’s account. How they were stolen is not reported. Der Spiegel’s sources add “possibly by means of agentic AI”.

Three incidents earlier in 2026 took or used developer or release credentials

The April incident is the closest precedent. A group that researchers identify as TeamPCP published mbt@1.2.48 and three @cap-js packages with a preinstall stealer that took GitHub and npm tokens, SSH keys and cloud credentials and sent them to GitHub repositories. The versions were live for two to four hours, and SAP documented the incident in Security Note 3747787 (reference 17). Germany’s BSI now rates the IT security situation “tense to critical” (reference 2).

Five judgements: two rest on reporting, two on the public record, one stays open

KJ-1

Attackers used stolen employee credentials to reach SAP’s development on GitHub.

Likely Moderate

Der Spiegel’s insider reports stolen tokens and altered code, and Handelsblatt’s company sources place the incident in software development. SAP confirms only “suspicious activities”. Our observations show a response in SAP’s development systems, not its cause. Confidence is Moderate: the token detail has one unnamed source.

Rests on: claims 3, 5 and 6 (page 4); E-01, E-03. Gap: SAP has not said how the tokens were taken or what they could write to. A statement from SAP on the access path would settle this either way.

KJ-2

SAP treated its build and release path as exposed, not only its source code.

Likely Moderate

Handelsblatt reports four measures: restricted GitHub access, stopped automated development processes, replaced signing keys and a rule that every code change be signed. Three of the four show in public: the OpenUI5 sync stopped, access to internal repositories was blocked, and signed commits rose from 6% to 34% of direct pushes. Signing keys are replaced when a release path is in doubt, not after read-only access to code. Confidence is Moderate: the key replacement itself has one outlet and is outside our view.

Rests on: claims 7 and 11 (page 4); E-01, E-03, E-15. Gap: Which keys, and whether anything was built or signed while the attackers had access. A notice of re-signed downloads or packages would raise confidence.

KJ-3

SAP’s response began on 18 or 19 November, about a week before the first report.

Very likely Moderate

The last commit synced from SAP’s internal Gerrit to UI5/openui5 is dated 18 November, 14:58 UTC. In 2026 the sync had missed only two weekdays, both German public holidays; it has now missed six in a row. On 19 November commits in SAP’s public organisations fell by more than half in a day, while three control organisations showed no comparable fall. From 20 November, committers who had not signed before began to sign. Confidence is Moderate: a planned freeze or an outage of the sync would look the same, and SAP has given no date.

Rests on: E-01, E-02, E-06, E-15 (page 6). Gap: SAP’s detection date, and how long the attackers had access before it. A statement from SAP on either would replace this estimate.

KJ-4

The affected environment includes SAP’s internal GitHub Enterprise, not only github.com.

Likely Moderate

A public SAP workflow that reads from github.tools.sap, SAP’s internal GitHub, was paused on 26 November “until required repos unblock access”, and the sync that stopped also starts inside SAP. The public organisations kept working: direct pushes by people were back at their usual level by 24 November, and provenance-attested packages kept publishing. Confidence is Moderate: two artefacts point inward and none at the public organisations, but tampering there that was later removed would leave no trace.

Rests on: E-01, E-03, E-08 (page 6). Gap: Whether the “GitHub presence” in Der Spiegel’s report means github.com, github.tools.sap, or both.

KJ-5

Whether altered code reached software that customers run cannot yet be assessed.

Not assessed

We found no attacker commit, campaign or worm indicator, or unusual CI change in the surviving public history of 186 SAP repositories. We also found no public copy of non-public SAP code and no report of a tampered SAP release (to 08:10 UTC, 27 Nov). Both are statements about the evidence: deleted branches, rewritten history and internal repositories are outside our view, and SAP’s statement covers customer business data only.

Rests on: claim 2 (page 4); E-10, E-11, E-16, E-17 (page 6). Gap: The repository names and the period of access. A named repository that feeds a shipped product or a public package would warrant an advisory the same day.

No attacker commit, worm indicator or leaked copy survives in public

Campaign indicators. The branch names, commit messages, file names and probe pull-request title of the wfx campaign appear nowhere in the 218,637 refs of 295 repositories or in the commits of the campaign window (E-10). The repository indicators of the Shai-Hulud worm family are absent too: its commit message, its loader and payload file names, its workflow file, its temporary branch and its forged co-author trailer (E-17).

Unusual pushes. Of 2,573 non-merge commits pushed directly by 334 committers since 2 November, six came from a UTC offset unusual for their committer, and none of the six touches CI, build or dependency files (E-11). Three bot identities went quiet after 18 November; each gap is inside that bot’s own range since 1 October, so we set them aside (E-12).

Copies. A clone leaves no public trace, so we looked for what a copy leaves when it is republished. Forks of SAP’s repositories did not rise after 18 November: 51, 36 and 40 a week from 2 November, and 26 on 23–27 November. Five same-named repositories that are not forks share commit history with SAP’s; all five mirror public TechEd workshop samples. No repository is named or described as a leak of SAP code (E-16).

What this silence cannot prove

This is surviving public history. Clones, deleted branches, force-pushes, private and internal repositories and Actions logs are outside it. Code copied from a non-public repository would show in public only if someone republished it, and a change that the attacker or SAP later removed would leave no trace. The 186 repositories are those pushed since 1 November, not every SAP repository.

A Shai-Hulud-family worm fits the reporting most closely, and we found no trace of it

The Shai-Hulud family, which researchers link to TeamPCP, poisoned four SAP npm packages in April and spread again in August. Its marker is still appearing: 206 repositories carrying it were created on GitHub on 24–27 November, under one account that matches no SAP committer (E-17). Its August variant used stolen GitHub tokens to commit hook files into repositories its victims could write to. The commit message was chore: update config, with a forged co-author trailer naming an AI coding agent and a start-up hook for that agent (reference 18).

That behaviour matches four reported details: tokens stolen from many employees, code altered on GitHub, “possibly by means of agentic AI”, and a tool that lets developers check their code for suspicious patterns (claims 5, 6, 8 and 12). Three things weigh against it. None of the worm’s indicators is in SAP’s 186 public repositories. The worm steals secrets, and the report says source code was copied. SAP has named no malware. We treat it as the hypothesis to test first (Q-1), not as a finding.

The AI remark has two other readings: an agent drove the stolen tokens, as in the Microsoft agent-framework case of 17 November (reference 16), or an agent’s own identity was the stolen one (R-4). A claim about tooling is not a claim about the actor.

ATT&CK mapping: six techniques, none confirmed by SAP

Four techniques restate claim 5 and inherit its status: Reported, from one insider. T1195.002 marks the open question of KJ-5 and applies only if altered code reached a release. T1588.007 marks the unconfirmed AI remark.

Attribution: none

Three hypotheses remain open: a state-linked intrusion for source code or an implant, financially motivated theft for extortion or sale, and spill-over from a token-harvesting campaign. The reporting we read carries no claim, demand or leak, and no public evidence is inconsistent with any of the three. The worm fit above favours spill-over without excluding the others: a stolen token can be sold or reused by a second actor. An implant in altered code or overlap with tracked infrastructure would favour the first; a demand or a sale the second; SAP naming an earlier campaign the third.

Appendix C: GitHub controls, two files in full and two excerpts

Pin every action to a full commit SHA, replace the placeholder names, and test in your own repository first. For C-7, create .github/upstream-tags.txt with git ls-remote --tags "$UPSTREAM" | sort -k2. For C-4, adopt commit signing before you enable the watch. C-6 is three settings for a consumer’s CI: npm ci --ignore-scripts, npm audit signatures, and a Dependabot cooldown of three days.

.github/workflows/upstream-watch.ymlC-7 · consumers and CERTs · tested live
# C-7: watch an upstream you depend on. Alert when its branch
# moves, when history is rewritten, or when a release tag moves.
name: upstream-watch
on:
  schedule:
    - cron: "17 * * * *"
  workflow_dispatch:

permissions: {}

jobs:
  watch:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      issues: write
    env:
      GH_TOKEN: ${{ github.token }}
      UPSTREAM: https://github.com/UI5/openui5
      BRANCH: master
      # the last head you reviewed
      PINNED: c586680fda4fa2c4b0bdc055a00ea39ff51e30c2
    steps:
      - uses: actions/checkout@v4
        with: { persist-credentials: false }
      - name: Branch moved, history rewritten, or tag moved
        run: |
          msg=""
          head=$(git ls-remote "$UPSTREAM" "refs/heads/$BRANCH" \
                   | cut -f1)
          if [ "$head" != "$PINNED" ]; then
            git init -q up
            git -C up fetch -q --filter=tree:0 "$UPSTREAM" "$BRANCH"
            if git -C up merge-base --is-ancestor \
                 "$PINNED" FETCH_HEAD 2>/dev/null; then
              msg+="$BRANCH moved to $head. "
            else
              msg+="HISTORY REWRITTEN at $head. "
            fi
          fi
          git ls-remote --tags "$UPSTREAM" | sort -k2 > tags.now
          moved=$(sort -k2 .github/upstream-tags.txt \
                    | join -1 2 -2 2 - tags.now \
                    | awk '$2 != $3 {print $1}' | tr '\n' ' ')
          [ -z "$moved" ] || msg+="TAGS MOVED: $moved"
          [ -z "$msg" ] && exit 0
          echo "::error::$msg"
          n=$(gh issue list --state open --json number \
                --jq length --search "upstream-watch in:title")
          [ "$n" -gt 0 ] || gh issue create \
            --title "upstream-watch: $BRANCH changed" --body "$msg"
          exit 1
.github/workflows/push-watch.ymlC-4 · publishers · logic tested
# C-4: catch a push to the default branch that skipped review.
# Rulesets should prevent it; this fires when a token with
# bypass rights pushes anyway.
name: push-watch
on:
  push: { branches: [main] }

permissions: {}

jobs:
  watch:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: read
      issues: write
    env:
      GH_TOKEN: ${{ github.token }}
      BEFORE: ${{ github.event.before }}
      AFTER: ${{ github.sha }}
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0, persist-credentials: false }
      - name: Each pushed commit is signed and came through a PR
        run: |
          bad=""
          for sha in $(git rev-list "$BEFORE..$AFTER"); do
            git cat-file commit "$sha" | sed '/^$/q' \
              | grep -q '^gpgsig' || bad+="$sha unsigned. "
            n=$(gh api "repos/$GITHUB_REPOSITORY/commits/$sha/pulls" \
                  --jq 'map(select(.merged_at != null)) | length')
            [ "$n" -gt 0 ] || bad+="$sha has no merged PR. "
          done
          wf=$(git diff --name-only "$BEFORE" "$AFTER" -- .github/ \
                 | tr '\n' ' ')
          [ -z "$wf" ] || echo "::warning::CI files changed: $wf"
          [ -z "$bad" ] && exit 0
          echo "::error::$bad"
          gh issue create --title "Unreviewed push to main" \
            --body "$bad CI files: ${wf:-none}. See the audit log."
          exit 1
